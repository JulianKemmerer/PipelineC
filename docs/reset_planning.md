# Reset planning for Pypeline HDL 

This document collects the requested reset behavior and the additional design
questions exposed by the Pypeline implementation. It is a planning document,
not an implemented API or a settled reset specification. **Requirements** below
record the requested behavior; **open decisions** and **recommendations** remain
choices to resolve before implementation.

Comparisons with Amaranth, Chisel and SpinalHDL appear alongside the relevant
decisions. Their documented behavior is precedent, not a requirement to copy
their defaults or an assertion that their reset systems solve Pypeline's
automatic-pipeline semantics.

Scope is the Python HDL, its native and generated-HDL simulation, the shared
compiler/backend paths it uses, and Pypeline libraries and examples. Legacy
StreamSoC source supplies application requirements for a future Pypeline port;
implementing reset in the C front end remains outside scope. The external
WireGuard Pypeline design also supplies concrete integration requirements.
Findings describe inspected source, not new synthesis measurements or executed
reset regressions.

The current planning focus is **user-facing syntax options**, shown in the
[syntax alternatives](#potential-user-facing-syntax) for StreamSoC, WireGuard
and PDW. No syntax is selected here. Keep compiler/VHDL
implementation choices for later; the implementation considerations below are
background constraints, not the next task. Prefer a small useful first feature
set that users can compose with ordinary logic, without requiring a large reset
standard library or every advanced scenario in this inventory at once.

## Requirements

1. **Reset is opt-in.** Designs that do not enable it retain their functional
   results, first-cycle work and simulation cycle numbering. They acquire no
   generated top-level reset signal, port or behavior. The preferred initial
   raw-VHDL interface is an explicit exception: a local implicit `RESET` port
   may remain, tied to zero when automatic reset is disabled.
2. Once enabled, provide an implied reset associated with clock/domain context,
   analogous to the implied clock and `CLOCK_ENABLE` plumbing, with explicit
   named access available too. A 100 MHz domain named `clk_100p0` should have a
   reset name such as `reset_100p0`. Raw `vhdl()` functions must be able to use it.
   Allow multiple resets on one clock and a shared asynchronous reset source
   serving multiple clocks; clock inference supplies a default, not a mandatory
   one-to-one mapping.
   Prefer separate reset declarations with optional clock association, and
   access to the selected reset through the clock object, such as `clk.reset`.
   Declaration syntax should make the reset style explicit rather than hide it
   behind `reset=True` or an unexplained `default=True`.
3. Support both top-level reset inputs and resets generated by internal logic,
   as clocks already support external inputs and internal sources. A
   synthesizable testbench must be able to generate reset for its DUT.
4. Define reset for user registers **and** registers inserted by automatic
   pipelining. The default is **active-high synchronous reset, with reset above
   clock enable in priority**. Reset updates selected registers even with CE low.
   Reset values, overrides and supported additional styles still need definition.
   Each user `Reg[T]` must support inheriting, opting into or opting out of reset.
   A plain `Reg[T]` has no automatic reset unless an enclosing policy enables
   it. Making a reset signal available on a clock does not itself enable that
   policy; an explicit opt-out is only needed to counter an inherited policy.
   The first version may require separate registers for different policies,
   such as resettable stream validity and unreset payload. Partial-field reset
   within one compound `Reg[T]` is a possible later extension, not an initial
   requirement.
5. Distinguish automatic register reset from user-written reset logic. Reading
   reset is not, by itself, an instruction to disable inherited reset for a
   whole function or hierarchy. Manual branches and explicit reset arguments
   elaborate as ordinary combinational next-state logic. Automatic register
   reset overrides the computed value at the reset event, including when both
   mechanisms use the same signal. They can coexist without a special overlap
   prohibition. Inheritance, generated state and ASIC coverage still need rules.
   Field/bit policy overrides can follow if partial reset is added later.
6. Give testbenches a way to drive reset explicitly, including during a run.
   For a reset-enabled domain with an eligible external reset, the default
   single-clock simulation applies **one cycle of synchronous reset at clock 0**,
   then deasserts it. A design without reset has no startup reset activity or
   reserved idle cycle. Define precedence with explicit/internal sources.
7. Specify CDC reset behavior, particularly asynchronous FIFOs: which side
   resets what, whether one-sided reset is supported, buffered-data loss,
   synchronization and restart readiness.
8. Audit Pypeline libraries and examples for reset compatibility, without enabling
   reset throughout existing code. PDW and the external WireGuard design are the
   first large adopters, alongside new examples. StreamSoC is not being modified;
   its first Pypeline version will copy the existing design, so the new reset
   feature must remain compatible with that future port. PDW will adopt resets
   primarily to remove reset-only FIFO drain/flush workarounds; preserve normal
   packet/algorithm flushing.
9. Allow register initial values without a reset only on FPGA targets that
   support the requested power-up initialization. On ASIC targets, a
   user-specified register initial value requires an effective reset.
   Distinguish user intent from compiler defaults and generated storage.
10. **RAM/ROM contents do not reset.** Their user-specified initialization is
    FPGA-only under the requested target policy. Reset surrounding control and
    interface registers as appropriate, retaining memory contents at runtime.
11. The first version needs no special `.valid` hooks or validity-driven reset
    optimization. Validity can be ordinary register state under ordinary rules.
12. Review CE semantics together with reset, especially delayed internal CE and
    freely clocked IO banks; existing CE implementation details are not fixed
    requirements for the new API. Include global-wire visibility and whether
    receivers can accept transfers while the producer is reset or disabled.
    Automatic reset/CE overrides of global-wire values remain an open question.
13. WireGuard will offer **optional synchronous reset, enabled by default**.
    When enabled, **one reset covers the entire selected design**, including
    both directions and all shared resources in the shared design. Its reset
    policy will be ASIC-compatible and cover almost all register state,
    including omitted-initializer `Reg[T]` declarations, nested library state
    and generated pipeline/FSM state. The reset-disabled option remains subject
    to target initialization rules; it does not waive ASIC requirements.
    This is broader than checking explicit initializers or clearing only valid
    bits. Memory contents remain subject to the separate no-reset rule.
14. **Reset overrides a ready/valid handshake:** a transfer at a reset edge is
    dropped, even if valid and ready would otherwise both be high. Stream outputs
    must have valid low during reset; ready should preferably be low too. For
    synchronous reset without combinational status gating, registered outputs
    take these values after the reset edge, and the edge itself cancels transfers
    despite any old high ready/valid values.

Active-low and asynchronous reset support, including their first-release scope,
remain to be decided. Exact FIFO ready/release timing also remains open within
the transfer-drop and low-valid contract; the preferred synchronous interface
avoids combinational reset-to-ready/valid paths. This stream-interface contract
does not settle whether arbitrary global wires need automatic overrides during
reset; see [global wires and CE](#global-wires-during-reset-and-clock-disable).

## Reset semantics and ownership

Keep four concepts separate:

- **Initial value:** state at power-up or at the start of a simulation, where
  the target supports it.
- **Reset source:** the physical signal and the domains that consume it.
- **Register reset policy:** active level, synchronous/asynchronous action,
  participation, reset value and priority relative to enable/write logic.
- **Protocol recovery:** which pending operations are canceled and when outputs,
  ready/valid flags and side effects are meaningful again.

The selected default is active-high synchronous reset. For automatically reset
state, the clock-edge priority is reset, then enabled normal updates, then hold.
With reset high and CE low, the register loads its reset value; it does not
capture ordinary input data. Async reset would additionally act without a clock
edge and needs its own explicitly supported contract.

Reset availability and automatic participation are separate. A clock can expose
a reset signal for manual logic while its registers retain ordinary no-reset
behavior. A surrounding policy can opt registers into automatic reset; explicit
per-register exclusion then overrides that policy. Syntax must distinguish the
source, participation and loaded value instead of overloading `reset=`.

Open decisions include whether initial and reset values must coincide, whether
additional polarities/styles belong in the first implementation, and which
settings can be overridden per MAIN, instance or function. Per-register reset
participation is required; its syntax and policy precedence remain open.
Per-field participation within one compound register may be deferred.
Typed reset values must cover signed/scalar values, enums, nested structs and
arrays, including unspecified aggregate elements. Reuse existing conversion
rules and diagnose unsupported types; do not silently coerce every reset to zero.
The existing explicit `char_t` register-initializer restriction is recorded in
the [issues inventory, #357](issues_inventory.md#invalid-hdl-crashes-and-misleading-errors).

Amaranth domains default to active-high synchronous reset; SpinalHDL defaults to
active-high asynchronous reset. These different defaults make explicit policy
and documentation necessary. See the [Amaranth domain guide](https://amaranth-lang.org/docs/amaranth/v0.5.4/guide.html#clock-domains)
and [SpinalHDL domain configuration](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Structuring/clock_domain.html#configuration).

### Inherited versus manual reset

The API needs to express these distinct cases, with syntax still undecided:

| Intent | Required meaning |
|---|---|
| Inherit | Use the enclosing participation policy and, where needed, its selected source. With no automatic policy, plain registers have no automatic reset. |
| Explicit reset | Select another named source/policy for this scope or register. |
| Manual reset | User expresses ordinary combinational next-state logic using a reset-valued signal. Automatic reset still overrides that value on participating registers. |
| No reset | Deliberately leave eligible state without runtime reset, subject to target initialization rules. |
| Observe reset | Read the signal for protocol control, diagnostics or other logic without changing register ownership. |

Manual reset can be an ordinary synchronous assignment such as `if rst: count = 0`.
It may assign only some fields, compute a nonconstant replacement or intentionally
preserve state. It does not describe asynchronous behavior merely because its
input is called reset. Treating such an assignment as ordinary enabled next-state
logic can also mean it never executes with CE low. It is not automatically
equivalent to the selected automatic reset priority.

**The composition rule is automatic reset over ordinary next-state logic.**
An `if rst` elaborates normally into muxes; using an implied reset read, a named
wire/input or an explicit function argument makes no difference to that rule.
The argument is an ordinary hardware input, not an automatic-reset binding.
The automatic reset value wins at the reset event on a participating register,
regardless of what that combinational logic computed. Reading reset or writing
such a branch neither opts out state nor requires a special ownership marker.
Without automatic participation, the branch has only its ordinary update/CE
behavior. This rule does not force combinational outputs to the reset value.

**Inheritance syntax remains open.** A function definition is reusable across
clock/reset domains, so do not bind a specific reset source on `@hw_func`.
Function metadata can describe inheritance rules. The actual signal comes from
the instance/call context or owning MAIN/clock; `with` scoping is preferred for
changing it around particular calls. Define how those rules affect children and
generated state. The initial version can require separate registers for
different participation policies; field-level declarations can follow later.

StreamSoC supplies a concrete nonconstant manual reset case: the legacy
[I2S receiver/transmitter](../include/i2s/i2s_mac.c) assigns `last_lr = lr` while
reset is active, alongside constant resets of its phase/count/valid state.
A fixed register reset value cannot replace that sampling behavior unchanged.
Preserve those ordinary manual assignments without enrolling the affected
registers in automatic constant reset. Treating this code as an asynchronous
constant reset would change its meaning.

Useful precedents separate context from per-register participation. Chisel has
scoped `withReset`/`withClockAndReset` contexts; Amaranth offers per-signal
`reset_less` and scoped `ResetInserter`; SpinalHDL's `ResetArea` can replace or
combine the enclosing reset. These are explicit controls, not a prescription
for detecting arbitrary manual reset branches. See [Chisel reset scopes](https://www.chisel-lang.org/docs/explanations/reset),
[Amaranth control-flow modifiers](https://amaranth-lang.org/docs/amaranth/v0.5.4/guide.html#modifying-control-flow)
and [SpinalHDL reset areas](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Structuring/clock_domain.html#resetarea).

Reset above CE also requires native simulation to reset affected instances when
Python control flow skips their calls. Only resetting functions that execute
that cycle is insufficient. ASIC initializer validation adds a separate proof
obligation: a manual branch might leave some initialized bits untouched or be
unreachable while disabled. See [target rules](#fpga-initialization-and-asic-targets).

### Per-register and partial reset

Reset participation must be expressible for each user `Reg[T]`: inherit the
surrounding policy, explicitly enable/select reset, or explicitly opt out despite
a reset-enabled context. An explicit selection can supply a reset where the
enclosing context has none. Reading reset for manual logic must remain separate
from these declarations.
The ordinary declaration needs no `reset=None` merely to remain unreset: absent
an inherited automatic-reset policy, no automatic reset is the default. Scope
selection can provide a source for a register that explicitly opts in. Exact
annotation spelling for participation and the loaded value remains undecided;
the `reg(...)` initializer helper is not a candidate.

**Partial-field reset may be deferred beyond the first version.** Start the
syntax examples with one policy per whole `Reg[T]`. When stream validity needs
reset but payload does not, declare separate valid and data registers and
assemble the stream value when used. This needs no special `.valid` hooks and
does not require splitting an otherwise uniformly reset compound register.

Separate **no reset assignment** from **hold while reset is asserted**. An
excluded register is not necessarily frozen: define whether ordinary enabled
updates continue, and show explicit user logic when holding is wanted. The
split-register example promises no particular payload while validity is zero.

A later field-level extension could express the same intent within one
`Reg[Stream[T]]`. It would need rules for nested fields, arrays, unspecified
fields and overlapping whole-register/field declarations. Keep those questions
out of the initial syntax requirement.

The ASIC initializer rule still applies per initialized bit. Splitting data and
valid does not legalize an explicit initializer on unreset data. Likewise, a
future partial reset of `.valid` would not justify initialization of the entire
stream. WireGuard's broad reset policy remains an application choice; separate
registers do not imply automatically removing its payload resets.

### Global wires during reset and clock disable

A combinational wire has a driven value, not stored state to reset. Resetting
its producer's registers does not automatically force every global output to
zero, and holding producer state with CE does not freeze combinational paths
from changing inputs. Any registers inserted on global-wire paths still need
their own storage policy.

The receiving state and the transfer contract determine whether a wire's value
matters:

| Boundary | Question to settle |
|---|---|
| All receiving state shares reset, and reset overrides updates | The receiver can ignore ordinary inputs at that reset edge. A blanket wire override may add no useful behavior. |
| A receiving register opts out, uses another reset, or is an external interface | It may still observe or capture the wire. Decide which producer/consumer logic prevents unwanted effects. |
| Producer and receiver share an effective CE | Disabled receivers can ignore changes, but the meaning and timing of the shared enable must be explicit. |
| Producer is disabled while the receiver can advance | A held-high stream `.valid` can cause repeated transfers without interface handling. Holding registers alone does not prevent this. |

For a stream carried by a global wire, making only `.valid` low may be sufficient;
payload need not be zero. Whether that behavior belongs in producer logic, a
wire declaration, or only the receiving state remains **open**, for reset and CE.
Do not require automatic global-wire masking or a new wire-reset API yet.
Preserve the agreed reset-edge transfer-drop/low-valid contract for reset-enabled
stream interfaces, including its synchronous timing distinction, while deciding
how those interfaces achieve it without an unwanted combinational reset path.

A register reset does not inherently suppress external side effects. Account
for RAM write enables and transfer acceptance at the boundary that owns them;
consider assertions and simulation observations separately from stored state.
Start with explicit user/library logic where needed, using ordinary fields and
named reset access. General output isolation and reset coordination helpers need
not be prerequisites for the first feature set.

## Clock inference, names and reset sources

### Domain identity and naming

Use clock identity, not frequency alone. Two clocks at 100 MHz with different
names require distinct defaults, for example `reset_100p0_rx` and
`reset_100p0_tx`. `syn_mhz` changes a timing target, not the physical domain;
it must not rename reset. Clock pin aliases and generated-clock bindings also
must not accidentally create duplicate reset sources.

The requested `reset_100p0` convention fits a 100 MHz clock. The compiler's
unassigned default clock is actually `(None, None)` and its clock-name helper
renders `clk_None`; it is not universally a 100 MHz default. Decide the reset
name for that case without inventing a frequency. See
[clock API identity](pypeline_DESIGN.md#make_clockmhz-name-syn_mhz--clocks) and
`VHDL.CLK_MHZ_GROUP_TEXT`.

Domain-level names and entity-local ports serve different purposes. Ordinary
entities currently receive local `clk`, not a hardcoded `clk_100p0`. The preferred
raw-VHDL spelling is `if RESET(0) = '1' then`, using a local implicit one-bit
reset mapped to the selected source when that instance participates. Also
provide explicit named-reset access in Pypeline without hierarchical references
to `top`. A one-line declaration such as `rst: Wire[uint1_t] = make_reset(...)`
should make `rst` the obvious runtime signal. Whether binding must occur on that
line, and whether an unbound reset object can itself be read, remain open.

An unopted design must not acquire a top-level reset port. Selecting a reset on
a clock identifies the signal accessible through `clk.reset`; it does not itself
turn on automatic reset for all registers. Reset may also be declared without a clock.
Keep source timing/provenance distinct from selecting a consumer's default.
Define pruning of enabled-but-unused resets and diagnostics for explicit
references where no reset is bound. Existing manual
signals named `rst` remain ordinary signals unless deliberately bound to the new
mechanism. Combinational designs and reset-free FPGA designs keep their interfaces.

Amaranth supports reset-less named domains and late-bound `ResetSignal` references.
Chisel instead infers an abstract `Reset`'s synchronous/asynchronous type from
connections, with incompatible mixtures rejected. That type inference is distinct
from Pypeline choosing a reset source through its clock connectivity graph. See
[Amaranth signal binding](https://amaranth-lang.org/docs/amaranth/v0.5.4/guide.html#late-binding-of-clock-and-reset-signals)
and [Chisel reset inference](https://www.chisel-lang.org/docs/explanations/reset).

SpinalHDL associates registers with the active clock-domain scope at creation.
Its domain includes reset and CE. Pypeline must define an equally clear binding
point across elaboration and re-parsing. See [SpinalHDL clock-domain scopes](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Structuring/clock_domain.html).

### Raw VHDL with reset disabled

**Preferred initial approach: one raw body with local `RESET` tied to zero when
automatic reset is disabled for the instance.** The author can always write
`if RESET(0) = '1' then`. This permits a local reset port/branch in rendered raw
HDL for a reset-disabled instance; it is the accepted exception to literal
absence of reset signals. It must not introduce a top-level reset input or
change existing behavior. Conditional no-reset bodies can be considered later;
they are not a prerequisite for the first version.

An ordinary explicit argument named `rst` is not this implicit port. It remains
whatever data signal the caller supplies and must not be tied inactive simply
because automatic reset is disabled. Raw text determines how it is used; the
compiler does not infer automatic-reset semantics from its name or contents.

Preserve supported FPGA declaration initialization when reset is absent,
expose the effective policy to the native model, and account for
different sync/async process structures. A tie-off does not satisfy ASIC reset
requirements. Opaque text cannot be assumed to adapt to any inherited style;
declare supported styles or generate the appropriate variant.

Chisel external modules make clock/reset ports explicit rather than supplying
implicit ones. This is a useful boundary precedent: the wrapper owns the wiring
contract, and the supplied HDL owns its internal reset behavior. Pypeline's
initial preference is an implicit local port with inactive tie-off. See [Chisel external modules](https://www.chisel-lang.org/docs/explanations/blackboxes).

### Multiple resets and shared reset sources

Clock inference can choose a default; it cannot determine every intended reset
boundary. PDW uses `ctrl_rst` and `global_rst` on the same 125 MHz clock so
configuration can be loaded while the datapath remains held. This is an existing
use case for multiple reset scopes on one clock, not only a hypothetical extension.
See [PDW reset sequencing](../examples/pypeline/dsp/pdw/README.md#reset).

Keep clock connectivity separate from reset selection. A shared wire or
`Inst[f]` between two reset scopes must not merge their resets automatically.
Define how a global instance or same-clock FIFO chooses its reset when its users
have different policies. Require a deliberate choice for an ambiguous shared
stateful resource. Communication between independently reset blocks also needs
a recovery contract even when both blocks share a clock.

Conversely, one asynchronous reset source can serve several clock domains.
Keep the source identity separate from each domain's conditioned reset and
release policy. Synchronizing release once in one domain does not make it safe
for every other clock; each consuming domain needs its own release handling,
including when a clock stops. A shared source does not merge those clock domains.

Amaranth's `ResetSynchronizer` takes an asynchronous source and a destination
domain, asserting asynchronously and releasing synchronously. That per-domain
interface is a useful precedent for sharing a source without sharing its
synchronized release. See [Amaranth reset synchronization](https://amaranth-lang.org/docs/amaranth/v0.5.4/stdlib/cdc.html#amaranth.lib.cdc.ResetSynchronizer).

Clock assignment adds global-instance/FIFO MAINs late. Reset resolution must
include those MAINs, imported modules, factory-generated functions and children
instantiated in multiple domains. Apply effective policy per instance rather
than mutating a shared function definition according to whichever caller is
visited first. See [global instances](PY_TO_LOGIC_DESIGN.md#global-instances-instf-fifot).

Sharing can also impose a reset boundary larger than one caller. WireGuard's
encrypt/decrypt graphs share compute MAINs through global wires while retaining
private packet state. Its single design-wide reset must reach both the private
state and independently declared shared MAINs. Reset inference must preserve
that common binding across the global-wire boundaries. See the
[WireGuard review](#wireguard-fpga-prototype-and-asic-reset-coverage).

### External and internal sources

Mirror clock binding where appropriate: one externally driven input or one
internally driven wire supplies a reset. Validate type, unique driver, unused
bindings, conflicting declarations and case-insensitive HDL name collisions.
An internal source must not also become an externally driven top-level reset.

Reset generators need their own policy. A counter that generates a DUT reset
must not inherit that same reset and continually return to its initial count.
PLL-lock conditioning, reset stretching and staged bring-up can similarly need
an independent root reset or explicitly reset-free FPGA startup state. Detect
direct dependency mistakes where practical and explain indirect dependencies
in diagnostics; do not promise that arbitrary user logic can be proven free
of reset deadlock.

Clock-generating logic needs attention too: holding the generator in reset can
stop the destination clock before a synchronous reset has reached its consumers.
The source clock/reset and the generated domain's reset are distinct dependencies.

On ASICs, an internally generated reset whose generator itself needs initialized
state cannot bootstrap from an unsupported declaration initializer. It needs an
external/root source or another explicitly supported hardware mechanism.

An external asynchronous source or a source from another clock needs a defined
crossing strategy. `ASYNC` currently permits a crossing; it does not insert a
synchronizer. Specify assertion, deassertion, minimum pulse observation and
clock-stopped behavior. A reusable reset conditioner can expose any hold/release
latency, rather than callers guessing a fixed number of cycles. Check the board
PLL-lock use in [Arty](../examples/pypeline/arty/top.py) and
[pico-ice](../examples/pypeline/pico_ice/top.py).

Reset sources can be outputs of opaque IP as well as ordinary user logic.
StreamSoC's Ethernet MAC exports distinct RX/TX clocks and resets; its DDR
interface exports UI reset and calibration status. Support representing those
existing connections and polarities. Preserve the distinction between a reset
signal and the DDR interface's existing reset-done/calibration status; this does
not require a new readiness supervisor or restart sequence for StreamSoC.
See the [StreamSoC review](#legacy-streamsoc-requirements-for-a-pypeline-port).

### Optional reset synchronization diagnostic

It would be useful to diagnose an asynchronous reset source used without
appropriate synchronization/conditioning for its receiving clock. This is a
**desirable diagnostic, not a prerequisite for the first reset implementation**.
Distinguish source timing from register reset style: selecting synchronous reset
does not make an external signal synchronous, while asynchronous assertion can
be intentional. For asynchronous register reset, the useful check is normally
whether release is synchronized separately to each receiving domain, as in the
[Amaranth reset synchronizer](https://amaranth-lang.org/docs/amaranth/v0.5.4/stdlib/cdc.html#amaranth.lib.cdc.ResetSynchronizer).

A separately declared reset may have no associated clock. When it is used in
a synchronous receiving domain, a synchronization/conditioning check is desired
rather than assuming the source is already synchronous. Missing association is
unknown timing, not proof that the signal is asynchronous. Choosing it as
`clk.reset` identifies a consumer, not evidence of synchronization. An explicit
association must not silently insert a synchronizer or bypass the need to state
what timing guarantee it represents. The initial diagnostic scope remains open.

The current `_check_clock_crossings` checks global-wire/pin clock associations
and records explicitly permitted crossings. For an `ASYNC` wire or pin,
`_crossing_hardware` reports `none`; it does not prove a reset synchronizer exists
downstream. See [the existing crossing report](PY_TO_LOGIC_DESIGN.md#the-crossing-report).
A reset check therefore needs some new reset-specific metadata, even if it
reuses that report rather than introducing another analysis subsystem.

A limited first check could use the resolved reset source, receiving domain and
recognized library/IP conditioning contract:

- Flag a known asynchronous or cross-domain source that directly controls reset
  without a recognized conditioner for that receiving domain. Report source and
  consumer locations; `ASYNC` permission alone is not synchronization evidence.
- Accept a known same-domain source or a declared, appropriate synchronizer/IP
  output. A release synchronized to clock A is not evidence for clock B, even
  when both clocks have the same frequency.
- Keep unknown/opaque implementations distinct from known unconditioned paths.
  Include sources with no clock association in this category rather than
  silently treating them as synchronous to their first consumer.
  Allow an explicit contract for raw VHDL or external conditioning; do not claim
  to recognize arbitrary manual synchronizer logic or prove physical CDC safety.

Exact metadata and warning/error policy remain open. Avoid automatically adding
synchronizer latency or changing a user's chosen assertion behavior. General
reset-domain-crossing analysis, arbitrary logic recognition and physical
recovery/removal signoff are outside this narrow proposal. Designs without reset
opt-in should not acquire reset diagnostics merely because a signal is named
`rst`.

## Automatically inserted registers

Reset must be physical control of the selected storage, not an ordinary input
that the pipeline mapper delays alongside transaction data. Existing CE behavior
is a caution: input registration can delay `CLOCK_ENABLE`, and
[#122](https://github.com/JulianKemmerer/PipelineC/issues/122) describes why this
does not act like an immediate whole-pipeline stall. The current
`VHDL.GET_PIPELINE_LOGIC_COMB_PROCESS_TEXT` still distinguishes delayed internal
CE from the freely clocked IO banks. Do not copy that data-alignment path for
automatic reset distribution.

**CE is open to revision alongside reset.** Decide what enable means at each
boundary: accepting an input, advancing internal state, updating an output bank,
or stalling an entire pipeline. Work through reset with CE low, registered CE
still in flight, and the first enabled edge after release. Resetting internal
state while freely clocked IO registers capture old data can otherwise leave
stale control or payload at the boundary. Do not freeze the current split merely
because it exists. Any revised CE behavior must preserve existing unopted designs
or have a separately explicit migration/opt-in; reset support must not silently
change their data or cycle behavior.

Other HDLs demonstrate that CE priority is a policy choice. SpinalHDL documents
CE above synchronous reset; its asynchronous reset is above CE. Amaranth's shown
composition of `ResetInserter` and `EnableInserter` gives reset priority over
enable. Pypeline selects reset above CE and must enforce it across all storage
banks. See [SpinalHDL generated signal priorities](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Structuring/clock_domain.html#signal-priorities-in-hdl-generation)
and [Amaranth control-flow modifiers](https://amaranth-lang.org/docs/amaranth/v0.5.4/guide.html#modifying-control-flow).

| Storage or boundary | Reset questions |
|---|---|
| `Reg[T]` user state | Initial versus reset value, per-register/manual ownership, CE priority and next-state visibility; partial-field policy can follow later. |
| Input/output banks (`io_registers_r`) | Reset data and control fields consistently, including registered CE and aligned global IO. |
| Stage registers (`REG_STAGE...`) | Which wires reset, to which values, and whether post-reset fill is observable. |
| Raw operator pipeline (`manual_registers_r`) | Partial carry/compare/arithmetic state and accumulated operands must obey the same contract as surrounding stages. This is compiler-generated raw HDL, distinct from user `vhdl()` text. |
| Fixed-latency blocks and alignment registers | Reset the alignment paths as well as the block; preserve declared latency and enable semantics. |
| AUTO_FSM control and shared units | Return to the correct idle encoding, cancel work/output-valid state and prevent old pipelined unit results from being captured after restart. |
| MULTI_CYCLE/AUTO_MULTI_CYCLE wrappers | Cancel an outstanding transaction, restart the wait counter and prevent an old capture/result from becoming valid. |
| Automatically pipelined RAM | Include routing/request bundles, write strobes, selection stages and response validity, not just RAM leaf outputs. |

References: [pipeline register lifetimes](AUTO_PIPELINE_DESIGN.md#3-pipeline-stages-and-register-lifetimes),
[raw operator stages](RAW_VHDL_DESIGN.md#slices-and-stages),
[FSM control](AUTO_FSM_DESIGN.md#the-control-path),
[multi-cycle stream wrapper](../include/pypeline/stream/stream_multi_cycle.py) and
[RAM register placement](AUTO_PIPELINE_DESIGN.md#ram-register-placement-and-splitting).

### Reset values are not equivalent to valid results

Zeroing every inserted register does not guarantee the result of executing the
source with zero inputs. For example, a stage after `x + 1` resets to zero under
that rule, although evaluating the expression with `x = 0` gives one. Reconvergent
paths, nonzero constants and arithmetic split across bits make this a semantic
choice, not just a VHDL assignment template.

The first version can use ordinary register reset rules for data and validity;
it needs **no special `.valid` hooks**, validity inference or automatic payload
reset removal. A library's valid bit is another register, with an appropriate
reset value. Choosing deterministic values for compiler-inserted registers and
documenting what scalar outputs mean during refill remain necessary. Do not
silently change a scalar API to mean “ignore this output for a while.”

Chisel's `RegInit` explicitly gives a register a reset value. This is a useful
ordinary-state model for validity as well as payload, but it does not specify
what values Pypeline should assign to newly inserted pipeline stages. See
[Chisel sequential circuits](https://www.chisel-lang.org/docs/explanations/sequential-circuits).

Users can explicitly leave payload unreset by declaring data and validity as
[separate registers](#per-register-and-partial-reset). Automatically removing
payload resets based on a validity/protocol proof is a separate, later
optimization; such proof and special validity APIs are outside the initial
requirement and must not become prerequisites for reset support.

For [make_stream_auto_pipeline](../include/pypeline/stream/stream_auto_pipeline.py),
reset must cover the valid path, its input/output registers, the output FIFO,
`in_flight` and `ready_reg` together. Clearing only the FIFO and credit counter
allows pre-reset pipeline results to refill the FIFO after release and corrupt
credit accounting. Apply the same rule to unequal-latency completion joins and
their metadata queues.

Release/refill behavior must use actual `.latency` or implementation metadata,
including enable-qualified advancement where relevant. A reset controller must
not silently insert extra datapath latency. Sweep changes, fixed latency zero,
boundary-only registers, nested pipelines and bit-internal cuts all need the
same externally stated reset contract. Reset fanout or timing may justify an
explicit distribution pipeline, but its skew and release protocol cannot be
chosen as ordinary data-path retiming.

## FIFOs and clock domain crossings

### Single-clock FIFO

A resettable FIFO should discard occupancy by resetting pointers, valid flags
and any pending response/output state. The separate FWFT output register counts
as storage: clearing only memory pointers can leave an old valid word visible.
Define acceptance and ready/valid values while reset is active and on the first
post-reset cycle, including reset with CE low, full/empty state, simultaneous
push/pop, wrapped pointers and a stalled output.

Write-side reset blocks writes; read-side reset blocks reads and clears output
validity. A reset edge drops ready/valid transfers, valid must be low during
reset, and ready should preferably be low too. For synchronous reset, retain the
preference for registered state changes over combinational
`ready/valid AND NOT reset` masks. The timing distinction is:

- Immediately before the reset edge, old ready/valid values may still be high.
  That edge cancels transfers even when ready and valid are high. Peers sharing
  reset, scoreboards and source/sink state must apply the same rule; after the
  edge the FIFO's reset state is visible.
- An independently reset peer cannot silently discard a transfer that the other
  peer counted as accepted. Coordinate quiescence/reset or provide an explicit
  recovery protocol. A purely local registered flag cannot retroactively cancel
  an external handshake.
- Suppress RAM write strobes and pointer advances at reset edges, even if CE is
  high or a request was already pending. Avoiding a combinational path to public
  ready/valid does not mean permitting internal memory writes during reset.
- After the first reset edge, read-valid stays low while reset is held. Prefer
  write-ready low too, even though reset has made the FIFO empty. Define the
  registered ready behavior and when normal readiness returns after release.
  This does not promise an immediate output change between clock edges: demanding
  low flags before the first synchronous reset edge would require revisiting the
  no-combinational-reset-path preference.

Asynchronous reset may change registered status between edges; that is distinct
from adding a combinational mask to a synchronous interface. Whether an async
implementation also needs such a mask remains an explicit interface decision.

Payload RAM **is not reset**. Occupancy and FWFT validity determine which retained
bits are meaningful; an empty FIFO's payload is not necessarily a promised zero.
Preserve ordering/capacity and normal push-to-valid behavior after restart.

Update the primitive, `make_fifo`, `make_stream_fifo` and global `Fifo[T]`
realization together. Replacing a global FIFO's implementation based on its
inferred clocks must not silently change its public reset/discard contract.

### Asynchronous FIFO

The current [async global-FIFO realization](PY_TO_LOGIC_DESIGN.md#async-global-fifos)
creates write/read MAINs on separate clocks and delegates storage to
`VHDL.WRITE_CLK_CROSS_ENTITIES`. It needs reset ownership for both ends, including
the binary/Gray pointers, synchronized pointer copies and output-valid state.

**Recommended first contract:** reset discards the entire FIFO and coordinates
both ends. Independent one-sided reset is a separate feature unless a protocol
is provided that prevents the other side from interpreting reset pointer values
as new data or free space. Define what happens if only one side requests reset:
propagation to the other side, refusal, or a supported recovery handshake.
Do not quietly reset just the local pointer.

Blocking writes at the write end and reads/valid at the read end is necessary
local behavior, but it does not by itself make independent pointer resets safe.
The synchronous no-combinational-status-path preference still needs a coherent
cross-domain request, cancellation and recovery protocol.

Amaranth makes this ownership explicit: its `AsyncFIFO` is emptied by the write
domain's reset, while a read-domain reset preserves the queue; an `r_rst` output
reports a write-triggered reset to the reader. This is one concrete asymmetric
contract, not an assumption that independently resetting both pointers is safe.
Pypeline must choose and document its own contract. See [Amaranth asynchronous FIFO](https://amaranth-lang.org/docs/amaranth/v0.5.4/stdlib/fifo.html#amaranth.lib.fifo.AsyncFIFO).

Specify behavior for unrelated rates/phases, equal-rate distinct clocks,
assertion/release in either order, short pulses, repeated reset and either clock
stopped. Release must wait for whatever synchronization or reset-busy protocol
the implementation requires. One edge in the write domain is not proof that
the read domain observed reset.

The XPM path is a separate adapter, not just the built-in FIFO with another
entity name. Its existing template comments require a write-clock-synchronous
reset and stable clocks on release, and it already exposes `wr_rst_busy` and
`rd_rst_busy`. Verify the selected vendor primitive's actual pulse and busy
requirements against its documentation during implementation; the embedded
template is labeled version 2019.1. Any pulse stretching/coordination needed by
that primitive must be represented in the wrapper's recovery contract. The
simulator's one-cycle default pulse is not permission to ignore those requirements.

### Other crossings

Review level/pulse synchronizers, reset request/acknowledgment logic and protocols
that compare toggle bits. Reset can itself create an apparent event if source
and destination state return to different epochs. Decide the reset values and
release ordering of synchronizer stages and any output isolation. Extend the
existing [crossing report](PY_TO_LOGIC_DESIGN.md#the-crossing-report) with effective
reset sources/policies or reference a shared reset report so users can inspect
these choices.

## Simulation and testbench control

### Default single-clock timeline

Without reset opt-in, simulation performs its existing work at clock 0. It adds
no reset pulse, empty startup step, skipped stimulus or cycle-number offset.
This compatibility rule applies even if a library becomes reset-capable.

For a reset-enabled single-clock design with a harness-driven external reset,
the required default is one synchronous reset cycle at clock 0. A precise
candidate interpretation, to make explicit in both backends, is:

| Time | Reset/observation |
|---|---|
| Before clock 0 | Initialize the harness, run initial hooks and drive the chosen external reset active before the first rising edge. |
| Clock 0 rising edge | Commit reset values; no normal transaction is accepted by blocks whose reset contract cancels work. This edge counts within `--run N`. |
| After that edge, before clock 1 | Deassert the default reset at a defined safe stimulus phase. |
| Clock 1 onward | Normal operation resumes; validity/refill or reset-busy rules still apply. |

The pulse at clock 0 is required only in that enabled/default-driver case;
hook ordering, observation phase and `--run N` accounting above need explicit
agreement. In particular, decide what a combinational return or `sim_print`
observes *before* the reset edge: synchronous reset does not retrospectively
initialize state before that edge on an ASIC.
With source declaration separate from automatic participation, also define
startup-driver eligibility for a declared reset used only by manual logic.
Do not silently add a startup pulse to existing ordinary `rst` inputs or infer
automatic register reset merely to make a harness eligible.

`pypeline_sim._run_clock_cycle` currently converges wires, performs a final
observation pass, then commits buffered register writes. The
[cocotb template](../src/COCOTB.py) explicitly establishes clock-low before its
first rising edge so it is genuinely labeled clock 0. Introduce reset without
offsetting one simulator's labels or hiding the extra edge from scoreboards.

ChiselSim separates `simulate`, which supplies a reset initialization procedure
for a `Module`, from `simulateRaw`, which leaves reset stimulus to the caller.
The useful precedent is an explicit harness contract. Pypeline's automatic
procedure must additionally respect reset opt-in and preserve existing cycle 0
behavior. See [Chisel simulation APIs](https://www.chisel-lang.org/docs/explanations/testing#simulation-apis).

### Explicit stimulus and source precedence

Provide user control through native testbench inputs/API, generated-HDL harnesses
and synthesizable Pypeline stimulus. Exact API/CLI syntax is open. A user must
be able to select a named reset, hold or pulse it, deassert it, reassert it
mid-run and disable the default startup driver when supplying a waveform.

There must be one driver. The default harness drives an eligible external reset
only; it must not force an internally generated reset or fight a user-supplied
testbench. Make the relationship between automatic startup, an explicit waveform
and an internal source visible in run metadata. Testbench counters/scoreboards
may need a separate reset scope so the logic scheduling a pulse keeps running.

The low-level `sim_call()` API currently treats each outermost call as one edge.
Preserve that behavior for existing reset-free callers, including tests that call
`sim_reset()` and immediately expect useful work. For reset-enabled callers,
decide how they explicitly request/drive reset and whether an optional harness
helper supplies startup stimulus. Do not hide an extra call or change what the
caller's first edge means.

### Reset a live domain, not the entire simulator

Keep `sim_reset()` as simulation-session cleanup unless a deliberate compatible
API change is made. A hardware pulse must affect only the selected reset scope,
retain reset-exempt state and memory, and obey synchronous/asynchronous timing.
Do not implement it by clearing all simulator dictionaries or recreating every
RAM/FIFO model. Restarting a RAM model from its `init` template is not equivalent
to resetting only the RAM interface's valid bits.

Reset-aware execution must cover committed and pending register writes,
AUTO_PIPELINE delay lines, fixed-latency alignment state, delayed global writes,
MAIN result queues, AUTO_FSM simulation and `@sim_model` state. The snapshot/
deep-copy discipline in `_call_sim_model` must survive convergence: repeated
evaluation in one cycle must not apply reset or advance state multiple times.
It must also handle a child that was used previously but is skipped during reset.

Opaque models need a reset protocol or access to the effective reset context,
including which state/memory is retained. Reconstructing the class is only valid
when that matches the hardware contract. Define support for callable models
using `copy_state=False` as well as ordinary copied models and `@hw_func` delegates.

Native simulation currently refuses multiple named clocks; the default cocotb
template also requires one external clock. Multi-clock reset tests can use the
existing [custom GHDL harness](../src/tests/pypeline_tests/inst/multi_clock_ghdl_test.py).
Do not make a multi-clock native event scheduler a hidden prerequisite of the
first reset feature. If asynchronous reset between edges is supported in HDL
before native simulation can model it, declare and diagnose that limitation.

`SIM.GET_SIM_GEN_INFO` already distinguishes external and internal clocks.
Extend shared simulation metadata for resets and make the cocotb, Verilator,
CXXRTL and other harness consumers honor it. Built-hardware simulation/replay
needs the same resolved reset topology and behavior as the artifact being run;
see [simulation of built hardware](SIM_DESIGN.md#simulating-built-hardware).

## FPGA initialization and ASIC targets

The requested rule is about target capability, not merely which executable runs
synthesis. Resolve it centrally alongside
[tool/part selection](SYN_DESIGN.md#2-choosing-a-tool). Account for FPGA parts,
`device_models`/sky130, the part-less PyRTL estimator and target-free elaboration
or simulation. Do not silently assume FPGA initialization when the target is
unknown; decide when validation can be deferred and when it must reject a build.

An ASIC register with an explicit user initializer needs an effective hardware
reset that establishes the promised value. Merely declaring a reset signal,
tying it inactive or mentioning it in unrelated logic is not enough. The compiler
must account for every initialized bit, including fields, slices, conditional
assignments and enable conditions. An arbitrary user-written `if rst` cannot be
assumed to establish that coverage, even if it looks like reset logic.

**Manual reset may therefore be insufficient for ASIC initializer approval.**
Define a compiler-understood declaration, a deliberately restricted verifiable
form, or an explicit primitive contract that identifies the bits, source, value
and reset event. Reject unproven coverage rather than silently blessing arbitrary
next-state logic. Exact syntax and acceptable proof remain open; do not promise
general analysis of Python control flow or opaque HDL. Manual logic can still
coexist with automatic reset: automatic reset overrides the ordinary next-state
value on participating registers.

The current omitted initializer is **not an uninitialized-state declaration**:
`VariableInfo.init = None` renders a typed zero/null and native simulation supplies
defaults. Distinguish those defaults from user-provided initializers. Decide
whether an explicit uninitialized/no-reset form is needed for new uses and how
to validate omitted initializers on ASICs. Existing reset-free FPGA/simulation
behavior must remain unchanged; inferred reset must never be enabled merely to
preserve a default.
The compiler must retain initializer provenance, including explicit zero versus
omission and source-user state versus generated control/data state. The latter
still needs correct behavior: a generated one-hot FSM cannot be exempted merely
because its `= 1` came from the compiler.

WireGuard makes this distinction practical: much of its state uses `Reg[T]`
without `= value`. Its requested ASIC migration needs broad inherited physical
reset even where the explicit-initializer checker has nothing to flag. Account
for register arrays and nested structs, generated arithmetic stages and opaque
library state. Report reset coverage and deliberate exceptions; do not infer
permission to leave payload registers unreset merely because validity is reset.
If required resettable register state would otherwise infer RAM, the lowering
must respect that reset contract or diagnose an unsupported implementation;
it cannot silently turn a register reset into memory initialization.

Other HDLs separate these concepts differently. Amaranth uses a signal's `init`
for power-up and, unless reset-less, reset. Chisel `RegInit` specifies the value
loaded on reset, not a promise of ASIC power-up state. SpinalHDL's `BOOT` domain
mode uses FPGA initialization without a reset signal. These precedents help
clarify terminology; they do not establish Pypeline's target legality policy.
See [Amaranth initial values](https://amaranth-lang.org/docs/amaranth/v0.5.4/guide.html#initial-signal-values),
[Chisel register reset values](https://www.chisel-lang.org/docs/explanations/sequential-circuits)
and [SpinalHDL reset kinds](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Structuring/clock_domain.html#configuration).

Separate these cases in the target check:

- Mutable user registers and generated sequential state.
- Read-only initialized registers that lower to combinational constants, versus
  storage with actual initialization. Define this distinction in the check;
  lowering to a memory must not silently bypass the memory policy.
- **RAM/ROM user initialization is FPGA-only.** On ASIC targets, reject it under
  the requested policy; adding reset to interface registers does not legalize
  memory initialization. This is a Pypeline rule, not a claim that ASICs cannot
  implement ROMs. Any future ASIC constant-ROM mechanism needs its own explicit
  contract, not implicit permission through the existing initialization API.
- Initializers hidden inside raw VHDL or external IP. A general Python register
  scan cannot validate these; require appropriate primitive/library contracts
  and backend checks rather than claiming exhaustive enforcement from text search.

RAM/ROM contents have no reset action. A runtime reset must retain RAM contents
and must not restore an `init=` image; ROM contents remain fixed. Reset relevant
request/response registers, write strobes, output registers and validity under
their own policies. Clearing memory by a sequence of writes is a separate user
operation, not an inferred reset implementation. Amaranth likewise presents
memory initial contents separately from its address/data/enable access ports;
that API separation is useful without adopting its initialization policy. See
[Amaranth memories](https://amaranth-lang.org/docs/amaranth/v0.5.4/stdlib/memory.html).

ASIC rejection of formerly accepted, unsupported initialization is an intentional
target-legality change. Diagnose it with the state and source location; do not
silently invent a reset or change behavior to make the design pass. Targeted ASIC
fixtures may need explicit migration, while reset-free designs on supported
targets retain the compatibility contract.

Do not substitute a simulation pulse or one-shot register initialized to one
for a real ASIC startup source. Tests must show that the reset reaches mapped
state, not only that the VHDL compiles.

Audit state by purpose. Existing libraries and examples generally need to become
**reset-compatible**, not automatically opt in to reset generation. Their callers
retain existing behavior until reset is enabled. When enabled, each block should
state what reset discards, preserves and makes valid, and implement the same
behavior in its HDL and model. Appropriate reset does not imply clearing RAM or
silently changing filter history. These are audit entry points, not a claim that
every library and example has already been exhaustively reviewed.

### PDW

PDW will convert to the new resets, primarily to replace FIFO flushing/draining
used only for reset. Its syntax examples should show the existing control and
datapath reset scopes, their retained configuration, and how FIFOs inherit the
appropriate reset. The repository-local integration cases are:

- Preserve staged control/datapath bring-up. Configuration intentionally survives
  datapath-only reset; a blanket domain-wide reset would destroy that feature.
- Reset FIFO occupancy and serializer state so reset completion need not depend
  on draining every stored beat. Revisit `RST_MIN_HOLD_CYCLES` only after the
  composed design, primitive busy times and pipeline refill have been verified.
- Preserve logical relationships: `pulse_measure` and `pulse_detect` must agree
  on the time-of-arrival epoch; resetting only one corrupts pulse intervals.
- The [PDW reset test](../examples/pypeline/dsp/pdw/pdw_reset_test.py) documents
  retained DSP history producing a release artifact handled by glitch rejection.
  Decide whether reset clears that history and update the contract/test deliberately.
- Test reset during a partial packet and with downstream ready low, then compare
  the contents of the first complete post-reset packet. “No output during reset”
  alone does not prove that old payload or descriptors were discarded.
- Update host bring-up/resynchronization instructions and tests with the hardware
  contract; do not leave obsolete minimum-hold guidance after removing a drain.

### Legacy StreamSoC requirements for a Pypeline port

The inspected design is [examples/stream_soc](../examples/stream_soc/), including
its CPU, shared DDR bus, Ethernet/audio, FFT and video peripherals and referenced
libraries. **No StreamSoC changes are planned; its first Pypeline version copies
the existing C design and its simple reset procedure.** The new feature and its
syntax must accommodate those existing reset signals, polarities and assignments
for future use, without requiring the port to adopt new inferred reset behavior.
The agreed transfer-drop/low-valid contract applies where the new feature is
deliberately enabled; it does not mandate retrofitting the original design.
This review does not add a transaction-cancellation protocol, bus-draining
procedure, late-response filter or coordinated subsystem-restart controller.

The [CPU device selection](../examples/stream_soc/cpu/hardware/devices.c) uses
Ethernet-delivered audio and leaves direct I2S commented out. The
[Arty wrapper](../examples/arty/board.vhd) contains commented StreamSoC reset
connections, including combining DDR reset/calibration and I2S readiness into
CPU reset. These are examples of intended wiring, not active connections
verified in a build. Keep that distinction when using them as porting references.

### Identity, caches and physical implementation

Reset style, values and interface shape that change entity text must participate
in physical implementation identity, including opaque-library configuration.
Passing different reset nets into otherwise identical entities need not prevent
reuse; emitting different reset behavior under one entity name must. Preserve
metadata through deepcopy, trimming, duplicate-instance collapse, repeated
elaboration, generated FSMs and selected RAM-plan replay. Invalidate affected
query/measurement caches and extend double-parse/name-stability checks. See
[entity identity](VHDL_DESIGN.md#entity-identity-and-reuse) and
[synthesis caches](SYN_DESIGN.md#6-caches).

An isolated synthesis wrapper must represent the implementation being measured.
Tying reset inactive can let synthesis remove reset muxes or control paths that
exist in the real top. Distinguish combinational operator characterization from
measurements intended to include resettable sequential boundaries.

Reset fanout, muxes, control sets and primitive reset capability can change area,
timing, retiming and RAM/DSP inference. Measure representative mapped hardware
with reset active as a real input. `DEVICE_MODELS` uses `dfflibmap` and its cheap
whole-design area estimate assumes one DFF cell; resettable cells and added muxes
need revalidation. Do not interpret its existing data-path STA as proof of
asynchronous recovery/removal analysis without checking that support.

Centralize reset-related constraint policy in `SYN.py` before adding similar
code to every backend. Synchronous reset paths are timing paths; asynchronous
reset release needs its own treatment. Do not blanket-false-path ordinary
manual reset logic or let data-path multi-cycle constraints accidentally relax
reset control. If reset-distribution timing is critical, retain/report that
evidence rather than attributing it to unrelated arithmetic and adding stages.
The inventory's [internal-clock Quartus issue, #137](issues_inventory.md#invalid-hdl-crashes-and-misleading-errors)
is a reason to verify actual hierarchical net matching for internally generated
reset constraints rather than copying names from a top-level alias.

## Decisions and implementation order

Settled requirements are opt-in with reset-free compatibility, active-high
synchronous default, reset above CE, an eligible default harness pulse at clock 0
only for reset-enabled designs, per-register opt-in/out, ordinary reset rules
without special `.valid` hooks, no memory-content
reset, FPGA-only memory initialization, and effective reset for explicit ASIC
register initializers. Reset drops ready/valid transfers at the reset edge;
valid is low in reset and ready is preferably low too, with synchronous
registered-output timing as described above. General global-wire reset/CE
overrides remain open.
Partial-field reset is not an initial requirement; separate registers can carry
different reset policies in the first version.

The selected semantic distinction is source availability versus automatic
participation: plain registers have no automatic reset without an inherited
policy. Manual reset branches and arguments are ordinary combinational logic;
automatic reset overrides their computed next-state value. Preferred syntax
directions are separate declarations, optional clock association and `clk.reset`
access, direct bound-signal use, `with` scopes and annotation-based controls.
Reusable definitions may specify inheritance rules but not a concrete source.
The preferred initial raw interface is `RESET(0)` tied to zero when inactive,
accepting its local rendered port/branch as the reset-free HDL exception.

Existing code becomes reset-compatible. PDW adopts resets primarily to remove
reset-only FIFO flushing. WireGuard offers synchronous reset enabled by default,
with one reset across the selected design and shared resources, covering almost
all register state for ASIC compatibility. StreamSoC has no planned changes;
its first Pypeline port copies the existing behavior, which the new reset
feature must accommodate.

### Syntax review in application context

The [syntax alternatives](#potential-user-facing-syntax) compare **how users
specify and use reset** at two main levels: global clock/reset declarations and
function/module register policy plus manual reset in Pypeline and raw `vhdl()`.
The examples are hypothetical, not implementation commitments. Compiler data
structures, inference algorithms and VHDL lowering remain outside this review.

| Example context | What each syntax option must make clear |
|---|---|
| Future StreamSoC port | How existing explicit reset inputs, polarities and manual assignments can be preserved, including `last_lr = lr`; where future inherited reset could be enabled without forcing a rewrite of the copied design. |
| WireGuard | One design option enables synchronous reset by default or disables it. Show the same choice reaching private and shared MAINs, library state and generated storage, plus intentional register exceptions. |
| PDW | Bind control/datapath resets separately, retain configuration through datapath reset, and reset FIFO occupancy without reset-only draining logic. |
| User register | No automatic reset by default absent policy; inherit, explicitly opt in or override an inherited policy. Distinguish source, participation and loaded value; use separate data/valid registers for differing policies. |
| Manual logic and interfaces | Read a bound or contextual signal, or pass it as ordinary data. Automatic reset overrides manual next-state computation. Show global stream-wire acceptance under reset/CE without assuming automatic masking. |
| Testbench and reusable block | Drive an external reset or generate one internally, keep the generator outside its own DUT reset, and instantiate a reset-compatible block with reset enabled or disabled. |

Favor a small core that covers these concrete needs. More elaborate sequencing,
isolation and synchronization helpers can follow user designs that need them;
the first version does not require a large reset standard library. A small
feature set still needs defined behavior for its supported registers, generated
state and interfaces.

Resolve these before fixing the API:

1. Independent declaration/binding syntax, optional clock association and
   `clk.reset` access, including absent-source and unbound-object behavior.
   Distinguish a source timing association from choosing a consumer's signal.
   Keep style explicit; avoid ambiguous boolean reset/default flags.
2. `with` scoping, function inheritance metadata, per-register participation
   and value syntax, unreset-register update/hold behavior and generated-state
   inheritance. Concrete source binding on `@hw_func`, `with_reset(func, ...)`
   and R2's `reg(...)` helper are excluded. Ordinary manual/automatic coexistence
   and automatic override are settled; ASIC proof of manual coverage remains open.
3. Initial versus reset values, explicit no-reset/uninitialized state, values for
   inserted pipeline stages and observable refill behavior. Review CE semantics,
   especially registered CE, freely clocked IO banks and global-wire visibility,
   without silently changing reset-free designs. Decide where receiver reset/CE
   is sufficient and where explicit interface control is needed; automatic wire
   overrides are not assumed.
4. Complete the preferred raw contract: implicit `RESET(0)` tied to zero for
   disabled participation, separate from ordinary explicit arguments. Preserve
   initialization and models. No-reset variants can wait; their strict-port-
   absence benefit is not an initial requirement.
5. FIFO whole-reset versus independent-end reset, registered ready/valid timing,
   synchronization and release readiness, with a realizable vendor adapter.
   Reset-edge transfer drop and low valid are settled; implement preferably-low
   ready while avoiding combinational reset-to-status paths for synchronous reset.
6. Exact clock-0 observation semantics for enabled designs, low-level `sim_call`
   control, manual-only source eligibility, stimulus precedence and native
   support boundaries for asynchronous/multi-clock reset.
7. Capability checks for unknown targets, omitted/default initialization and
   opaque IP, and explicit migration of ASIC fixtures affected by stricter
   initialization legality. The RAM/ROM no-reset and FPGA-only initialization
   rules are requirements, not deferred policy choices.
8. Whether the optional reset synchronization diagnostic fits the first version:
   source/conditioner metadata, recognized IP/library contracts and warning/error
   policy. Do not make a general reset-specific CDC analysis a prerequisite.

Implementation sequencing follows the syntax review and selection of the first
supported feature set. The [backend considerations](#compiler-and-backend-responsibilities),

simulator queues and opaque storage must not retain undocumented pre-reset work.

## Potential user-facing syntax

**All reset APIs in this section are proposals, not supported syntax.** The
examples describe user-visible declarations and behavior, not implementation.
Application bodies are abbreviated, and no project source changes are implied.
The preferred directions are separate reset declarations, `clk.reset` access,
`with` scopes at use sites, annotation-based register controls, and an implicit
raw-VHDL `RESET` port that is tied inactive when unused.

Keep three decisions distinct: **which signal is available**, **which registers
participate automatically**, and **what value reset loads**. Declaring or reading
a signal does not enable automatic reset. These sketches use `auto_reset=` for
participation and `reset_to=` for the loaded value solely to make that separation
visible. Those keyword names are still candidates, not accepted API spellings.
The ambiguous `reset=`/`reset_value=` register pair needs clearer vocabulary.

The `reg(...)` declaration helper and `with_reset(func, ...)` binding are excluded
from the active options. A function definition must not bind a particular reset
signal with `@hw_func(reset=...)`; definition metadata may describe inheritance
rules instead. Partial-field reset remains possible later work; the examples
use separate registers when policies differ.

### Global clock and reset declarations

Prefer a separate declaration whose reset style is visible. A one-line binding
makes the runtime signal unambiguous:

```python
# Proposed global declarations; source available, no automatic register policy.
core_rst: Input[uint1_t] = make_reset(kind="sync", active="high")
core_clk = make_clock(100.0, reset=core_rst)
```

Here `core_rst` is the signal used in manual hardware logic, and `core_clk.reset`
refers to that same selected signal. The `reset=` on the clock receives a named
signal, not a boolean that leaves the style unstated. This association makes the
source available to that clock's consumers; it does **not** reset every register.
Neither `reset=True` nor `make_reset(..., default=True)` is a preferred spelling:
the former hides the style, and the latter does not say whose default it changes.

A clock can also exist before a reset is declared. An alternative association
spelling is a property assignment during elaboration:

```python
# Proposed alternative; internal source driven by a hardware function.
core_clk = make_clock(100.0)
core_rst: Wire[uint1_t] = make_reset(
    kind="sync", active="high", clock=core_clk
)
core_clk.reset = core_rst
```

The assignment syntax is a candidate, not a requirement that the property be
writable. The desired capability is to declare independently, optionally
associate, and retrieve the selected signal from the clock. A reset's optional
`clock=` association must have a defined meaning; it must not silently select
it as every register's automatic reset. A clock may have multiple available
resets even though `clk.reset` identifies one selected default signal.

Source timing also needs a separate meaning. An unassociated reset used in a
synchronous receiving domain should receive the desired synchronization check.
`kind="sync"` describes the requested reset action, not proof that an external
input is synchronous. Selecting a signal as `clk.reset` does not synchronize it
or certify its release. If a `clock=` association is also used to declare a
timing guarantee, that contract must be explicit and distinguishable from merely
choosing a consumer. No automatic synchronizer insertion is implied.

One-line `Input`/`Wire` bindings are preferred for readability but are not yet
mandatory. For a possible split declaration:

```python
# Alternative declaration form under discussion, not an extra runtime signal.
reset_description = make_reset(kind="sync", active="high")
core_rst: Input[uint1_t] = reset_description
```

Decide whether an unbound object can itself be used in `if reset_description`,
or whether binding is required before any hardware read. Do not leave users
guessing which of two names is the real signal. The working examples use the
bound name directly. If both names are allowed as runtime references, they
must unambiguously identify the same signal. This question also affects implicit
port creation and the `reset_100p0` naming convention; it does not justify
creating a second driver or reset input.

Manual use of a bound active-high signal is ordinary Pypeline logic:

```python
# Inside hardware logic; neither expression changes automatic reset policy.
if core_rst:
    count = 0
if core_clk.reset:
    pending = 0
```

The two expressions observe the same signal. Decide how `clk.reset` represents
absence; `None` at elaboration is one candidate. Also define direct-read polarity
before adding active-low declarations: an ordinary input bit and an
asserted/not-asserted view must not become silently interchangeable. The initial
examples use active-high signals so that question does not obscure the syntax.

The context precedents in
[Amaranth domains](https://amaranth-lang.org/docs/amaranth/v0.5.4/guide.html#clock-domains)
and [SpinalHDL clock domains](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Structuring/clock_domain.html)
remain useful. Pypeline additionally needs an explicit distinction between an
available signal and the decision to automatically reset state.

**Use-site scoping is preferred for selecting a different reset around calls.**

```python
# Proposed scope: select the source, leaving participation policy inherited.
with reset_scope(control_rst):
    result = control_block(inputs)

# Proposed scope: additionally enable automatic reset for state in this region.
with reset_scope(control_rst, auto_reset="enabled"):
    result = control_block(inputs)
```

These show two uses of the same scope form. Changing the selected signal alone
does not enable automatic reset where no policy exists. Enabling the policy
covers ordinary registers and generated state in the region/callees, subject
to explicit exclusions and library contracts. It does not reset RAM contents.
Different instances of `control_block` may inherit different sources; the
function's definition remains reusable.

`@hw_func` can describe inheritance without naming hardware, for example a
candidate `@hw_func(auto_reset="inherit")`. The exact metadata and supported
inheritance rules are open. Selecting a specific signal belongs at a MAIN or
instance/call context, not on the reusable definition. A separately declared
shared MAIN is another root and needs its own effective policy; a scope around
one client's call does not silently govern the shared engine.
The role of such a region parallels
[Chisel reset scopes](https://www.chisel-lang.org/docs/explanations/reset) and
[SpinalHDL reset areas](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Structuring/clock_domain.html#resetarea).

### Register declarations and values

Use the annotation to express participation, keeping the initializer position
for a value. The following names make the concepts explicit while their final
spelling is undecided:

```python
# Proposed declarations INSIDE a hardware function.
data: Reg[uint32_t]                              # inherit policy; none by default
valid: Reg[uint1_t](auto_reset="enabled", reset_to=0)
history: Reg[uint32_t](auto_reset="disabled")     # overrides an enabled parent
count: Reg[uint16_t] = 7                         # initializer does not enable reset
```

`data` needs no explicit exclusion when no enclosing policy requests automatic
reset. If a parent enables automatic reset for all registers, the same plain
declaration inherits it. `history` demonstrates the case where an exclusion is
needed. `valid` opts in using the available contextual source. Explicit enable
without a source needs a diagnostic or another explicit source selection; it
must not silently invent a reset. A `with` scope can supply that selection.

| Concept | Candidate notation/meaning |
|---|---|
| Available source | Bound `rst`, `clk.reset`, or a source selected by `with reset_scope(rst)`. |
| Participation | Omitted / `auto_reset="inherit"`, explicit `"enabled"`, or explicit `"disabled"`. Inheritance bottoms out at no automatic reset. |
| Reset assignment | `reset_to=...` identifies a typed value to load; it is not a signal or a source-selection option. |
| Power-up initializer | `= value` retains its initialization role, subject to target support. It does not independently enable automatic reset. |

The loaded-value rule remains open. One candidate uses the explicit initializer
when a participating register omits `reset_to`, otherwise the type's zero/null;
an explicit `reset_to` can specify a different reset value. A simpler option
requires reset and initialization values to coincide and has no separate value
keyword. These examples use the first candidate to expose the distinction, not
to settle it. Chisel's
[`RegInit`](https://www.chisel-lang.org/docs/explanations/sequential-circuits)
remains a reset-value precedent rather than an ASIC power-up promise.

Annotation controls must compose with the existing multi-cycle tag slot, for
example `Reg[T, timing_tag](auto_reset="disabled")`; do not repurpose that slot
as a reset signal. An explicit initializer on unreset state remains subject to
the ASIC rule. Omitting it does not promise an ASIC power-up value.

Separate registers cover different payload/valid policies without field masks:

```python
word_stream_t = make_stream_t(uint32_t)

@hw_func
def sample_stage(word: uint32_t, take: uint1_t) -> word_stream_t:
    data: Reg[uint32_t]
    valid: Reg[uint1_t](auto_reset="enabled", reset_to=0)
    out: word_stream_t = word_stream_t(data=data, valid=valid)
    if take:
        data = word
    valid = take
    return out

# Inside a caller with an available reset but no all-register reset policy:
with reset_scope(core_rst):
    sampled = sample_stage(word, take)
```

Only `valid` opts in here. If the caller instead enables automatic reset for the
whole region, `data` inherits it too; add an explicit exclusion only if data
must remain unreset in that context. This is a valid-only sample register, not
a complete ready/valid buffer. At a reset edge `valid` loads zero despite
`take`; an unreset `data` follows its ordinary enabled updates. A candidate
opt-out rule is therefore no reset assignment, not implicit hold. The returned
stream uses old register values, preserving the distinction between pre-edge
observation and synchronous reset taking effect. The per-register distinction
has a precedent in
[Amaranth reset-less signals](https://amaranth-lang.org/docs/amaranth/v0.5.4/guide.html#reset-less-signals),
without requiring Pypeline to copy its default participation policy.

### Manual reset in Pypeline HDL

Manual reset is ordinary combinational next-state logic, including when an
automatic reset is active on the same register. A reusable function still needs
a way to observe its contextual source without hardcoding a global name. The
proposed `reset_signal()` below is one spelling for that access, not a separate
reset mechanism or a required wrapper around an already bound signal:

```python
# Proposed annotation/access syntax. Called each clock in this sketch.
@hw_func
def counter_step(step: uint1_t) -> uint8_t:
    count: Reg[uint8_t](auto_reset="enabled", reset_to=3)
    previous: uint8_t = count
    rst: uint1_t = reset_signal()
    if rst:
        count = 9
    elif step:
        count = count + 1
    return previous
```

The `if` computes an ordinary mux result of nine when `rst` is high. At the
automatic reset edge, the register loads three instead. There is no conflicting
ownership to infer and no reason to disable automatic reset because the body
reads the signal. Automatic reset overrides the combinational value; it does
not rewrite the combinational graph or force the returned old value to three
before the edge.

An explicit argument has exactly the same ordinary dataflow role:

```python
@hw_func
def counter_step_explicit(step: uint1_t, rst: uint1_t) -> uint8_t:
    count: Reg[uint8_t](auto_reset="enabled", reset_to=3)
    previous: uint8_t = count
    if rst:
        count = 9
    elif step:
        count = count + 1
    return previous

# Inside a caller; source selection and the ordinary data argument are distinct.
with reset_scope(core_rst):
    previous = counter_step_explicit(step, core_rst)
```

Passing `core_rst` as an argument alone does not select it for automatic reset.
If a different ordinary argument is high while the automatic source is low,
the mux can load nine on an enabled update. If the automatic source is high,
three wins regardless of the argument. A bound wire/input read behaves the
same way. Thus `reset_signal()` observes source availability, not whether this
particular register participates automatically. Its spelling, absent-source
behavior and relation to direct `clk.reset` access still need a single clear
API; it must not hide automatic enrollment.

For manual-only state, a plain register suffices under the default policy:

```python
# No inherited automatic-reset policy in this example.
@hw_func
def track_lr(lr: uint1_t, advance: uint1_t, rst: uint1_t) -> uint1_t:
    last_lr: Reg[uint1_t]
    previous: uint1_t = last_lr
    if rst:
        last_lr = lr
    elif advance:
        last_lr = lr
    return previous
```

Only under an inherited all-register policy would `last_lr` need an explicit
exclusion to preserve its input-dependent reset assignment. This function must
be called/enabled for its ordinary branch to execute. Automatic reset has
priority over implicit CE; an ordinary manual branch does not acquire that
priority. Keeping the block clocked and putting the normal-work enable inside
it allows a user to express manual priority over that enable. Arbitrary manual
logic still does not prove ASIC initializer coverage.

Global wires likewise have ordinary driven values. An acceptance observation
can express `incoming.valid & ready & ~core_rst`, but does not itself reset a
queue or force a public valid/ready wire low. CE holding a producer's state
also needs an appropriate receiver acceptance rule. No automatic global-wire
masking API is selected by these examples.

### Manual reset in raw VHDL

**Preferred implicit interface: `if RESET(0) = '1' then`.** A participating raw
instance receives the selected automatic source through this local port. The
raw author writes the behavior of private state; it is not inferred from text:

```python
# Proposed implicit RESET; active-high synchronous reset, above CE.
@hw_func
def raw_hold(x: uint8_t, step: uint1_t) -> uint8_t:
    vhdl("""
signal held : unsigned(7 downto 0);
begin
process(clk)
begin
  if rising_edge(clk) then
    if RESET(0) = '1' then
      held <= (others => '0');
    elsif CLOCK_ENABLE(0) = '1' then
      if step(0) = '1' then
        held <= x;
      end if;
    end if;
  end if;
end process;
return_output <= held;
""")

# Inside a caller; the scope chooses automatic participation for this instance.
with reset_scope(core_rst, auto_reset="enabled"):
    held = raw_hold(x, step)
```

**Start with one body and an inactive tie-off.** When automatic reset is
disabled for this instance, implicit `RESET` is tied to zero even if a reset
signal is available for manual use elsewhere. The raw port and branch remain
in emitted HDL; this is the preferred initial exception to literal reset-free
absence. No top-level reset input or startup activity is added merely to supply
the tie-off. Separate no-reset bodies and elaboration queries are not required
for the first version.

The excerpt has no power-up initializer, so the disabled form promises no
value before a capture. Existing FPGA wrappers must retain their supported
initialization behavior. The implicit interface does not make arbitrary raw
state resettable or natively simulatable, and a sync-only body must not silently
accept an asynchronous policy. Models and raw contracts must match the body.

**An ordinary explicit argument is a data port, not a second implicit reset
mechanism.** For example, this raw function uses `rst` to compute its ordinary
next value while implicit `RESET` still controls the register's reset action:

```python
@hw_func
def raw_value_select(x: uint8_t, rst: uint1_t) -> uint8_t:
    vhdl("""
signal held : unsigned(7 downto 0);
signal next_held : unsigned(7 downto 0);
begin
next_held <= to_unsigned(9, 8) when rst(0) = '1' else x;
process(clk)
begin
  if rising_edge(clk) then
    if RESET(0) = '1' then
      held <= to_unsigned(3, 8);
    elsif CLOCK_ENABLE(0) = '1' then
      held <= next_held;
    end if;
  end if;
end process;
return_output <= held;
""")
```

The argument participates as ordinary wiring in the surrounding function graph;
the raw body itself is opaque to Pypeline and explicitly authors the mux and
priority shown here. Disabling automatic reset ties only implicit `RESET` low.
It does **not** tie the ordinary `rst` argument low, remove its logic, or change
the caller-supplied value. Existing raw IP can also use an ordinary port in
its own sequential reset branch; that behavior belongs to the supplied body
and is not inferred automatic-reset policy. The explicit-port boundary remains
consistent with the precedent from
[Chisel external modules](https://www.chisel-lang.org/docs/explanations/blackboxes).

### PDW syntax examples

The source topology in [PDW's top](../examples/pypeline/dsp/pdw/top.py) has one
125 MHz clock, `global_rst` from seven channel resets, and `ctrl_rst` from
`tx0_s_axis_rst` alone. The preferred direction gives each existing internal
signal its reset declaration directly, with no extra reset-handle name:

```python
# Proposed global declarations; the property assignment spelling is tentative.
pdw_clk = make_clock(125.0)
global_rst: Wire[uint1_t] = make_reset(kind="sync", active="high", clock=pdw_clk)
ctrl_rst: Wire[uint1_t] = make_reset(kind="sync", active="high", clock=pdw_clk)
pdw_clk.reset = global_rst
```

Both remain internally driven wires. The existing FPGA generator can keep
ordinary plain registers, because source association does not enable automatic
reset in its MAIN:

```python
@MAIN(pdw_clk)
def rst_main():
    rst_r: Reg[uint1_t] = 1
    ctrl_rst_r: Reg[uint1_t] = 1
    global_rst = rst_r
    ctrl_rst = ctrl_rst_r
    rst_r = (rx0_s_axis_rst | tx0_s_axis_rst | rx0_m_axis_rst
             | rx1_m_axis_rst | rx2_m_axis_rst | tx0_m_axis_rst
             | tx1_m_axis_rst)
    ctrl_rst_r = tx0_s_axis_rst
```

The source registers preserve the existing one-cycle delay and FPGA startup
value. This is not an ASIC bootstrap scheme. If a wider policy also covers the
generator, it needs an explicit exclusion from the reset it generates.

The consuming MAINs opt into automatic reset. A call scope selects control
reset without binding the reusable function definition:

```python
# Proposed MAIN participation metadata; signal defaults to pdw_clk.reset.
@MAIN(pdw_clk, auto_reset="enabled")
def ctrl_main():
    with reset_scope(ctrl_rst):
        ...  # Control receiver and register-bank calls inherit ctrl_rst.

@MAIN(pdw_clk, auto_reset="enabled")
def pdw_main():
    ...  # Datapath state, FIFO calls and generated stages use global_rst.

@MAIN(pdw_clk, auto_reset="enabled")
def pulse_gen_main():
    ...  # Same automatic policy and global_rst source.
```

An equivalent spelling could put `auto_reset="enabled"` on a `with` region
inside each MAIN instead. The key is that this policy is explicit and distinct
from assigning `pdw_clk.reset`. Ordinary `@hw_func` definitions inherit at use:

```python
@hw_func
def config_bank(new_config: pdw_ctrl_t, write: uint1_t) -> pdw_ctrl_t:
    regs: Reg[pdw_ctrl_t] = CTRL_DEFAULTS
    current: pdw_ctrl_t = regs
    if write:
        regs = new_config
    return current
```

Inside `ctrl_main`'s region, the bank inherits automatic reset to
`CTRL_DEFAULTS` under the candidate value rule. A simultaneous write loses to
control reset. Datapath-only reset leaves the bank available for configuration.
The same definition used without automatic policy does not acquire a reset
just because it has an initializer.

The inherited FIFO call can retain its existing shape:

```python
packet_fifo = make_stream_fifo(sample_t, depth=PACKET_DEPTH)

@hw_func
def buffer_samples(in_stream_if: packet_fifo.fwd_t,
                   out_stream_if: packet_fifo.fb_t) -> packet_fifo.return_t:
    return packet_fifo(in_stream_if, out_stream_if)
```

Under `pdw_main`'s automatic policy, the future reset-compatible FIFO discards
occupancy even with output stalled; reset no longer needs `ready | global_rst`
to drain it. Upstream pipelines, serializers and models must support the same
contract before removing the workaround. Normal packet/discard flushing remains.
Manual PDW logic reads `global_rst` or `ctrl_rst` directly; those reads neither
disable nor enable the inherited automatic reset.

### WireGuard syntax examples

WireGuard still needs one optional synchronous reset, enabled by default, for
all private and shared resources. A proposed common project configuration can
declare its signal and its all-register policy separately:

```python
# Proposed project parameter and reset declarations.
use_reset = param("RESET", default=True, type=bool)
wg_clk = make_clock(wireguard_env.TARGET_MHZ)
if use_reset:
    wg_rst: Input[uint1_t] = make_reset(kind="sync", active="high", clock=wg_clk)
    wg_clk.reset = wg_rst
wg_register_policy = "enabled" if use_reset else "disabled"
```

Here `param`'s `default=True` is the ordinary default of a clearly named project
option, not the rejected ambiguous reset-domain flag. `clock=wg_clk` must carry
the documented association meaning, not silently certify physical synchronization.
All selected roots use the common configuration, including shared engines:

```python
@MAIN(wg_clk, auto_reset=wg_register_policy)
def encrypt_main():
    ...

@MAIN(wg_clk, auto_reset=wg_register_policy)
def decrypt_main():
    ...

@MAIN(wg_clk, auto_reset=wg_register_policy)
def chacha20_pipeline_shared():
    priority_encrypt: Reg[uint1_t]
    grant_stalled: Reg[uint1_t]
    stalled_is_encrypt: Reg[uint1_t]
    ...  # Existing arbitration and pipeline calls.
```

The three shared registers are from the external
`src/chacha20/chacha20_pipeline_shared.py`. Their plain declarations inherit the
explicitly enabled policy; source association alone would not suffice. Private
contexts, selected Poly1305 services, library state and compiler-created stages
need the same coverage. With the candidate value rule, omitted initializers use
typed zero; nonzero control encodings need their correct reset values. A rare
intentional exception can opt out in its annotation. Do not treat the ability
to separate payload and valid as permission to reduce WireGuard's broad coverage.

Conceptually `-D RESET=False` omits the new input and disables the inherited
automatic policy. No automatic harness startup cycle is reserved. Raw wrappers
can retain local `RESET` tied to zero under the preferred initial interface.
Target initialization rules still apply. This is a proposed parameter use, not
a runnable command for the existing design. The single enabled reset covers
both directions and shared engines; there are no per-direction reset choices.
The [behavioral requirements](#wireguard-fpga-prototype-and-asic-reset-coverage)
still cover owner/result alignment, aborted work and output validity.

For a synthesizable FPGA testbench, choose a `Wire` binding instead of the
hardware `Input` binding, using the same signal name. The stimulus MAIN has no
automatic policy, so it keeps running while the DUT is reset:

```python
# Alternative testbench configuration, with use_reset enabled; ONE binding.
wg_rst: Wire[uint1_t] = make_reset(kind="sync", active="high", clock=wg_clk)
wg_clk.reset = wg_rst

@MAIN(wg_clk)
def reset_stimulus():
    cycle: Reg[uint32_t] = 0
    wg_rst = (cycle == 0) | (cycle == 200)
    cycle = cycle + 1
```

The counter's initializer is a testbench FPGA assumption, not DUT ASIC reset
coverage. Internal stimulus replaces the default external driver; they must
not drive together. Reset-disabled reusable library instances keep their
ordinary behavior, including any explicitly supplied manual arguments.

### Future StreamSoC syntax examples

The first Pypeline version copies the existing design. It can retain ordinary
reset inputs and branches without using any new automatic-reset declaration:

```python
# Illustrative future port; no new reset participation policy.
cpu_clk = make_clock(CPU_CLK_MHZ)
areset: Input[uint1_t]

@MAIN(cpu_clk)
def cpu_top():
    rst: uint1_t = xil_cdc2_bit(areset)
    ...  # Copied CPU call and existing sticky-flag reset assignments.
```

`xil_cdc2_bit` denotes a future wrapper preserving the existing C helper, not
an assertion that a Pypeline wrapper already exists. The CPU's ordinary `if rst`
continues to select next values for PC/state; calling its input `rst` adds no
automatic policy, special CE priority, extra startup pulse or reset coverage.
I2S likewise keeps its explicit active-low argument and `last_lr = lr` sampling
branch. No new transaction cancellation or reset supervisor is required.

If a later design wants to describe the synchronized CPU signal using the new
mechanism, it can do so without enabling reset for every register on that clock:

```python
# Optional future use, NOT a planned StreamSoC change.
cpu_rst: Wire[uint1_t] = make_reset(kind="sync", active="high", clock=cpu_clk)
cpu_clk.reset = cpu_rst

@MAIN(cpu_clk)
def cpu_reset_source():
    cpu_rst = xil_cdc2_bit(areset)

# Inside a function under a scope selecting cpu_rst, with no all-register policy:
# pc: Reg[uint32_t](auto_reset="enabled") = 0
# state: Reg[cpu_state_t](auto_reset="enabled") = cpu_state_t.FETCH_START
# last_lr: Reg[uint1_t]  # Manual sampling remains ordinary logic, if relevant.
```

The per-register annotations here opt only the intended state into automatic
reset. A scope such as `with reset_scope(cpu_rst)` selects that source at use,
leaving the reusable definition free of a concrete signal binding. Manual
branches can coexist; if they compute a different value for participating
state, the automatic reset value wins. Input-dependent manual-only state must
not accidentally inherit automatic reset to a constant. It needs an exclusion
only if an enclosing policy would otherwise enroll it.

Existing active-low MAC/IP ports remain ordinary explicit raw arguments. The
new implicit `RESET` tie-off must not change their manually wired behavior.
The original memory initialization, reset/status wiring and nonzero startup
values remain as described in the [source review](#legacy-streamsoc-requirements-for-a-pypeline-port).

### Choices to review together

| Topic | Preferred direction and remaining choice |
|---|---|
| Declaration and association | Declare reset separately with visible style; allow optional clock association and retrieve the selected signal through `clk.reset`. Exact binding/property syntax remains open. |
| Runtime name | Prefer direct use of the bound `Input`/`Wire` name. Decide whether one-line binding is required and whether an unbound reset object can be read directly. |
| Unassociated source | Check suitability for the receiving synchronous domain; association or a sync-style label must not silently substitute for synchronization. Diagnostic scope remains open. |
| Reusable functions | No concrete source binding on `@hw_func`; inheritance metadata is allowed. Prefer `with` scopes for call-site selection. |
| Register policy | Plain registers have no automatic reset without an inherited policy. Keep annotation controls; choose clearer participation/value vocabulary instead of R2's `reg(...)` helper or overloaded `reset=`. |
| Manual logic | Ordinary mux/next-state computation, including explicit arguments. Automatic register reset overrides its result; merely reading reset never changes participation. |
| Raw VHDL | Use implicit `RESET(0)`, initially one body tied to zero when automatic participation is disabled. Ordinary explicit arguments remain live data ports. |
| Initial scope | Whole-register policies and separate data/valid registers suffice; partial fields, broader CDC analysis and elaborate reset libraries can follow concrete needs. |

The syntax spellings are still under review. Source availability, automatic
participation, manual dataflow and the preferred raw-port tie-off should remain
distinct in every alternative, without choosing compiler implementation here.
